## 🎯 Objetivos de aprendizaje

* Importar módulos creados en distintos programas.

* Organizar un proyecto sencillo en varias carpetas y archivos.

---

## 📚 Explicación teórica

### 1. ¿Qué es un módulo?

Un **módulo** es un archivo de Python (`.py`) que contiene código reutilizable (funciones, clases, variables).
Ejemplo: `math`, `os`, `sys`.

Además de los módulos estándar y externos, es posible **crear módulos personalizados**.

---

### 2. Creación de un módulo propio

```python
# utilidades.py
def saludar(nombre):
    return f"Hola, {nombre}!"

def sumar(a, b):
    return a + b
```

Uso en otro archivo:

```python
# programa.py
import utilidades

print(utilidades.saludar("Ana"))
print(utilidades.sumar(3, 4))
```

---

### 3. Formas de importar

```python
import utilidades                 # importa todo
from utilidades import saludar    # importa solo lo necesario
import utilidades as u            # alias
```

---

### 4. Paquetes en Python y `__init__.py`

Un **paquete** es una carpeta que agrupa varios módulos y que contiene un archivo especial `__init__.py`.

* Si la carpeta **no tiene** `__init__.py`, Python la trata como una carpeta normal.
* Si la carpeta **tiene** `__init__.py`, Python la reconoce como un **paquete**.
* El archivo `__init__.py` puede estar vacío o incluir importaciones y código de inicialización.

Ejemplo de estructura:

```
mi_proyecto/
│── main.py
│── utilidades/
│   │── __init__.py
│   │── cadenas.py
│   │── matematicas.py
```

En `main.py`:

```python
from utilidades.matematicas import sumar
from utilidades.cadenas import contar_letras
```

---

### 5. Diferencia entre carpetas y paquetes en Python (Python 3.3+)

Desde **Python 3.3**, gracias a los *namespace packages* (PEP 420), una carpeta **sin `__init__.py` puede ser importada** si se encuentra en el `PYTHONPATH`.
* **PEP 420** (*Python Enhancement Proposal 420*) introduce el concepto de **namespace packages**.
* Un *namespace package* es un paquete que **no necesita un archivo `__init__.py`** para ser reconocido por Python.

No obstante, el uso de `__init__.py` **sigue siendo recomendable** por claridad, control de imports y buenas prácticas.


| Aspecto | Carpeta sin `__init__.py` (namespace package) | Paquete con `__init__.py` |
| ------ | --------------------------------------------- | -------------------------- |
| Reconocido por Python | ✅ Sí (Python ≥ 3.3) | ✅ Sí |
| Importaciones | Posibles, dependen de cómo se ejecute el programa | Naturales y predecibles |
| Inicialización | ❌ No | ✅ Puede ejecutar código |
| Control de API | ❌ No | ✅ Sí (`__init__.py`) |
| Claridad | Baja | Alta |
| Uso recomendado | ❌ No | ✅ Sí |
| Uso en proyectos reales | ⚠️ Casos avanzados | ✅ Estándar |

---

#### Ejemplo sin `__init__.py` (namespace package) ⚠️

> Funciona **solo si el proyecto se ejecuta correctamente desde la raíz**.

```
mi_proyecto/
│── main.py
│── utilidades/
│   └── matematicas.py
```

`main.py`:

```python
import utilidades.matematicas

print(utilidades.matematicas.sumar(3, 4))
```

⚠️ **Limitaciones**:
- Puede fallar según el IDE o la forma de ejecución
- No permite centralizar imports
- No es recomendable para docencia ni proyectos estructurados

🚫 No se recomienda usar `sys.path.append()`, ya que es un hack frágil y poco mantenible.

---

#### Ejemplo con paquete (`__init__.py`) ✅ (recomendado)

```
mi_proyecto/
│── main.py
│── utilidades/
│   ├── __init__.py
│   ├── matematicas.py
│   └── cadenas.py
```

`matematicas.py`:

```python
def sumar(a, b):
    return a + b
```

`__init__.py`:

```python
from .matematicas import sumar
```

`main.py`:

```python
import utilidades

print(utilidades.sumar(5, 3))  # 8
```

---

**Conclusión**

Aunque desde Python 3.3 no es obligatorio usar `__init__.py`, su uso sigue siendo una **buena práctica** y la opción recomendada para proyectos educativos, profesionales y reutilizables.

---

### 6. Organización de proyectos

Buenas prácticas básicas:

* Mantener un archivo principal (`main.py`) como punto de entrada.
* Crear módulos separados para funciones reutilizables.
* Usar nombres claros y descriptivos.
* Convertir carpetas en paquetes cuando el proyecto crezca.

Ejemplo simple:

```
proyecto_notas/
│── main.py
│── notas.py
│── utilidades.py
```

Ejemplo con paquete:

```
gestor_tareas/
│── main.py
│── gestor/
│   │── __init__.py
│   │── tareas.py
│   │── utils.py
```

## 💻 Ejemplos prácticos

Ejemplo 1 — Módulo de operaciones:

```python
# operaciones.py
def cuadrado(x):
    return x * x

def cubo(x):
    return x * x * x
```

```python
# main.py
import operaciones

print("2 al cuadrado:", operaciones.cuadrado(2))
print("3 al cubo:", operaciones.cubo(3))
```

---

Ejemplo 2 — Reutilizar un módulo en varios programas:

```python
# saludos.py
def hola():
    return "¡Hola!"

def adios():
    return "¡Adiós!"
```

```python
# app1.py
import saludos
print(saludos.hola())
```

```python
# app2.py
from saludos import adios
print(adios())
```

## 📝 Actividad guiada — `gestor_tareas_modular`

Organiza un **mini proyecto** en varios archivos que funcione como un gestor sencillo de tareas.

### 🔹 Estructura del proyecto

```
gestor_tareas/
│── main.py
│── gestor/
│   │── __init__.py
│   │── tareas.py
│   │── utils.py
```

### 🔹 Detalles de cada archivo

1. **`tareas.py`**

   * `cargar_tareas()` → lee las tareas desde `tareas.txt` (si no existe, devuelve lista vacía).
   * `guardar_tarea(tarea)` → añade una nueva tarea al archivo.
   * `listar_tareas()` → devuelve todas las tareas en forma de lista numerada.

2. **`utils.py`**

   * `mostrar_menu()` → imprime el menú de opciones.
   * `pedir_opcion()` → pide un número válido (1, 2 o 3).

3. **`__init__.py`**

   * Centraliza las importaciones:

   ```python
   from .tareas import cargar_tareas, guardar_tarea, listar_tareas
   from .utils import mostrar_menu, pedir_opcion
   ```

4. **`main.py`**

   * Importa directamente el paquete `gestor`.
   * Muestra un menú con opciones:

     ```
     1. Ver tareas
     2. Añadir tarea
     3. Salir
     ```
   * Ejecuta la acción correspondiente.

# 📝 Actividad Evaluable — Proyecto Libre con Librería Externa en Python

## 📌 Descripción general

En esta actividad final el alumnado deberá **diseñar y desarrollar una aplicación en Python** utilizando **una librería externa de libre elección**, instalada mediante el gestor de paquetes `pip`.

El proyecto tiene como finalidad integrar y aplicar de forma práctica los contenidos trabajados en la **Unidad 3**, incluyendo el uso de módulos estándar, librerías externas, modularización del código y organización de proyectos.

Como parte de la actividad, cada alumno o alumna realizará una **exposición oral con una demo funcional** del proyecto ante el resto de la clase.

---

## 🎯 Objetivos de la actividad

* Aplicar el uso de librerías externas en Python.
* Integrar módulos estándar para ampliar la funcionalidad de una aplicación.
* Organizar un proyecto en varios archivos y módulos.
* Desarrollar una aplicación funcional y robusta.
* Explicar y demostrar el funcionamiento de una aplicación desarrollada.

---

## 📚 Elección de la librería externa

Cada alumno o alumna deberá elegir **una librería externa de Python** que sea de su interés personal o profesional.

La librería podrá pertenecer a cualquier ámbito, por ejemplo:

* Videojuegos y gráficos.
* Inteligencia artificial y aprendizaje automático.
* Análisis y visualización de datos.
* Desarrollo web o aplicaciones.
* Automatización, scraping o consumo de APIs.
* Otros ámbitos, previa validación por el profesorado si fuera necesario.

### La librería elegida debe cumplir los siguientes requisitos:

* Debe instalarse mediante `pip`.
* Debe utilizarse de forma real dentro del proyecto.
* Debe tener un papel relevante en la funcionalidad de la aplicación.

---

## 💻 Desarrollo de la aplicación

### 1. Funcionalidad

* La aplicación debe ser **funcional y ejecutable**.
* Debe hacer un uso claro y justificado de la librería externa elegida.
* La funcionalidad de la aplicación debe estar directamente relacionada con las capacidades de la librería seleccionada.
* La aplicación puede ser de **consola o gráfica**, según el tipo de proyecto.

---

### 2. Interacción con el usuario

* La aplicación debe permitir **interacción con el usuario**, por ejemplo:

  * Introducción de datos.
  * Selección de opciones.
  * Visualización de resultados o acciones.
* La interacción debe ser clara y comprensible.

---

### 3. Uso de módulos estándar

* El proyecto debe utilizar **al menos un módulo estándar de Python** (por ejemplo: `os`, `sys`, `math`, `random`, etc.).
* El uso del módulo estándar debe estar **justificado** y aportar utilidad real a la aplicación.

---

## 🗂️ Organización del proyecto

El proyecto deberá estar **correctamente organizado**, siguiendo buenas prácticas de programación:

* El código no debe estar concentrado en un único archivo.
* Se deben crear **módulos personalizados** para separar responsabilidades.
* Cuando sea necesario, se deberán usar **paquetes** (carpetas con archivo `__init__.py`).
* Los nombres de archivos, carpetas y funciones deben ser claros y descriptivos.

---

## ⚠️ Control de errores

La aplicación debe incluir **control de errores** para evitar fallos durante la ejecución:

* Gestión de errores habituales, como:

  * Entradas incorrectas del usuario.
  * Errores relacionados con la librería externa.
  * Situaciones imprevistas durante la ejecución.
* El control de errores debe mejorar la **robustez y estabilidad** de la aplicación.

---

## 📄 Documentación del proyecto

El proyecto debe incluir un archivo **`README.md`** con la siguiente información:

* Descripción breve de la aplicación.
* Librería externa utilizada y finalidad de la misma.
* Instrucciones para instalar las dependencias.
* Instrucciones para ejecutar la aplicación.
* Descripción general del funcionamiento.

Además, el código debe estar **comentado de forma clara y coherente**.
